# CloudOps Agent 面试问答手册

> 这是针对本项目整理的高频面试问题及答案要点。
> 目标：让你在面试中被问到项目时，能清晰、有条理地讲清楚「做了什么、为什么、怎么做」。

---

## 一、项目概述（开场必答）

### Q：用一句话介绍你的项目？

> 我做了一个「CloudOps Agent」云原生智能运维助手：它能用自然语言对话，帮我查询、诊断 Linux / Docker / Kubernetes 环境。技术上整合了大模型对话、RAG 知识库检索、工具调用（Function Call）三大 Agent 核心能力，最后用 Docker 打包、部署到 K8s。

### Q：为什么做这个项目？

> 我是云计算专业的学生，想把「大模型 / Agent」这个热门方向和我的专业（Linux/Docker/K8s）结合起来。这个项目正好两头占——既学了 Agent 全流程，又用到了运维知识。而且它是我「从零到完整」一步步做出来的，每个阶段都能讲清楚为什么这么做。

### Q：项目分几个阶段？为什么这么分？

> 分四个阶段，由简单到复杂，每步都能跑通：
> 1. **最小 Agent**：先接一个大模型 API，做多轮对话，理解 Prompt 和记忆
> 2. **加 RAG**：接入知识库检索，让 Agent 能"查资料"回答私有知识
> 3. **加工具**：实现 Function Call，让 Agent 能真正执行 kubectl/docker 命令
> 4. **容器化**：用 Docker 打包、部署到 K8s

---

## 二、Agent 核心概念

### Q：什么是 Agent？和普通大模型有什么区别？

> 普通大模型只会"说"（根据输入生成文字），Agent 会"做"。Agent 由四部分组成：大模型（大脑）、工具（手脚）、记忆（上下文）、规划（决策）。区别在于 Agent 能调用外部工具获取真实数据、执行真实操作，形成「思考→行动→观察→再思考」的闭环。

### Q：什么是 ReAct？你的项目里怎么实现的？

> ReAct 是 Reasoning + Acting，即「推理 + 行动」交替进行。我的项目里是手写循环：
> 1. 大模型思考，输出「要调用哪个工具、传什么参数」（Function Call）
> 2. 程序执行工具，拿到结果
> 3. 把结果喂回大模型，让它基于结果继续思考或回答
>
> 我**手写这个循环而不是用 LangChain 内置 Agent**，是为了看清每一步，真正理解原理。

### Q：什么是 Function Call（工具调用）？

> 大模型不只是输出文字，还能输出一个结构化的「函数调用请求」（工具名 + 参数 JSON）。程序解析这个请求、执行对应的真实函数、把结果作为消息返回给大模型。关键点：工具的参数要定义清晰的 JSON Schema，大模型调用才准确。

## 三、RAG 相关

### Q：什么是 RAG？为什么需要它？

> RAG = 检索增强生成（Retrieval-Augmented Generation）。大模型有知识截止时间、也不知道你的私有数据，直接问容易"幻觉"（编造）。RAG 的思路是：回答前先从知识库检索相关资料，把资料和问题一起给大模型，让它基于真实资料回答。

### Q：RAG 的完整流程？

> 1. **离线建库**：文档切分（chunk）→ 向量化（Embedding）→ 存入向量数据库
> 2. **在线检索**：用户问题向量化 → 相似度检索 → 取 top_k 个最相关片段
> 3. **增强生成**：把片段拼进提示词，大模型基于资料回答

### Q：关键词检索 vs 向量检索的区别？

> - **关键词检索**：字面匹配。问"容器崩了"匹配不到"CrashLoopBackOff"。
> - **向量检索**：语义匹配。把文本转成向量，用余弦相似度算语义接近程度，"容器崩了"能命中"CrashLoopBackOff"。
>
> 我的项目是「先关键词跑通流程，再升级向量检索」的演进，因为向量检索需要 Embedding API。

### Q：为什么要切分（chunk）？

> 文本太长会稀释相关性（一段里有很多无关内容），太短会切断语义。所以要控制长度（我用了固定长度 + 重叠），在"相关性"和"语义完整"之间平衡。

### Q：向量数据库为什么选 Chroma？

> Chroma 是轻量级、本地可持久化的向量数据库，适合学习和中小规模场景，不需要单独部署服务。我用的是 chromadb 原生 API 而不是 LangChain 的封装，为了少依赖、原理清晰。

## 四、云原生 / 运维相关（你的专业优势区）

### Q：项目里工具调用是怎么"真正操作环境"的？

> 工具层通过 `subprocess` 执行真实的 `kubectl` / `docker` 只读命令，比如 `kubectl get pods`、`docker ps`。我做了「自动降级」：检测到本机没有 kubectl/docker 时回退到模拟数据，保证演示不中断。

### Q：为什么工具只做"只读"，不做删除/重启？

> 安全考虑。运维 Agent 如果直接暴露删除、重启等危险操作，一旦大模型判断失误就会造成生产事故。所以工具层只暴露查询命令，危险操作需要额外的安全确认（白名单 + 权限控制），这是生产级 Agent 的设计原则。

### Q：Docker 镜像构建，为什么先 COPY 依赖再 COPY 源码？

> Docker 构建分层、每层有缓存。依赖清单（requirements.txt）很少变，源码频繁变。把依赖安装放前面，改代码重新构建时，依赖层命中缓存，不用重新下载安装，构建速度大幅提升。

### Q：API Key 怎么进容器？为什么不能写进镜像？

> 通过 `docker run --env-file .env` 或 K8s 的 Secret 注入。如果 COPY 进镜像，密钥会永久存在镜像层里，`docker history` 能还原出来，等于泄露。所以密钥必须运行时注入，与镜像分离。

### Q：Secret 和 ConfigMap 的区别？

> ConfigMap 存普通配置（明文），Secret 存敏感数据（API Key、密码）。Secret 底层是 base64 编码（不是加密，只是防"一眼看到"），真正的安全靠 RBAC 权限控制谁能读。

### Q：Deployment 和 StatefulSet 的区别？

> Deployment 管无状态应用（Pod 可随意替换，如 Web 服务）；StatefulSet 管有状态应用（需要稳定标识和存储，如数据库）。我的 Agent 是无状态的，用 Deployment。

## 五、追问 / 开放题

### Q：如果让这个项目更完善，你会怎么做？

> 1. **加 Web 界面**：现在是命令行，加个前端做可视化的对话和运维面板
> 2. **接真实监控**：接入 Prometheus/Grafana，让 Agent 能查真实指标
> 3. **多智能体协作**：拆分成「规划 Agent」「执行 Agent」「诊断 Agent」分工协作
> 4. **安全加固**：危险操作加二次确认、操作审计日志

### Q：这个项目最大的收获是什么？

> 不只是会用 LangChain，而是理解了 Agent 的**工作原理**——为什么大模型能调用工具、RAG 怎么减少幻觉、怎么把机制和实现分离。还有工程上的习惯：先跑通再优化、敏感信息不进镜像、绝对路径比相对路径可靠。

## 六、可能被问的"反面"问题（提前想好）

### Q：你这个项目和网上现成的教程有什么区别？

> 大部分教程是「照着抄跑通就完」，我这个是**带着问题逐步演进**：关键词→向量的升级是为了解决"字面匹配不到语义"的真实问题；模拟工具→真实命令是为了解决"没环境也能先跑机制"。每一步演进都有明确的动机，这是照抄教程做不到的。

### Q：RAG 的效果怎么评估？

> 可以看检索命中的准确性（问"容器崩了"是否命中"CrashLoopBackOff"）、回答是否引用了知识库的真实内容（而非泛泛而谈）。我专门写了 test_vector.py 做检索验证。

### Q：为什么不用更主流的框架（如 AutoGen / CrewAI 多智能体）？

> 学习阶段，理解原理优先。手写 ReAct 循环能看清每一步，比直接用封装好的多智能体框架更有收获。理解了底层，以后用框架也知道内部在做什么、出问题能定位。
