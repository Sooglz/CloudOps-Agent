# 阶段③ 说明：接入工具调用

这一页讲清楚阶段③做了什么、工具调用是什么、以及面试要点。

---

## 一、工具调用（Function Call）是什么

前面的阶段，Agent 只会"说"——根据知识库和自身知识生成文字回答。

阶段③让 Agent 会"做"——它能真正调用工具（比如查 Pod、看日志），拿到真实数据后再回答。

**核心机制**：大模型不只是输出文字，还能输出一个结构化指令，告诉程序"我要调用 `get_pods` 这个工具，参数是 `namespace=default`"。程序执行工具拿到结果，把结果再喂回给大模型，大模型基于结果组织回答。

## 二、ReAct 循环（思考—行动—观察）

这是 Agent 区别于普通聊天机器人的核心：

```
思考（大模型判断需要工具）→ 行动（调用工具）→ 观察（拿到结果）→ 再思考 → ... → 回答
```

学名 **ReAct**（Reasoning + Acting）。面试必讲。

## 三、阶段③做了什么

1. **定义工具**：`src/tools.py`
   - `get_pods`：查 Pod 列表
   - `get_nodes`：查节点资源
   - `get_container_logs`：查容器日志
   - 当前是「模拟工具」返回预设数据，先把机制跑通

2. **实现 Agent 循环**：`src/agent.py`
   - `ToolCallingAgent` 类，手动实现 ReAct 循环
   - 用 `llm.bind_tools()` 让大模型知道有哪些工具

3. **升级主程序**：`src/app.py`
   - 接入带工具调用的 Agent

## 四、怎么跑

```bash
cd D:\Work\CloudOps-Agent\src
..\.venv\Scripts\python.exe app.py
```

然后试这些问题（能触发工具调用）：

```
你 > 集群里有哪些 Pod？
你 > 集群的节点资源怎么样？
你 > flask-app 这个 Pod 的日志报错了，帮我看看
```

如果 Agent 返回的是"模拟数据里的真实内容"（比如列出了一堆 Pod 名字和状态），而不是泛泛而谈，就说明工具调用成功了。

## 五、关键设计：工具层可替换（模拟 → 真实）

这是阶段③最重要的设计，和阶段②的"检索器可替换"一脉相承：

```python
# 现在是模拟工具
def get_pods(namespace="default"):
    return "模拟的 Pod 数据"

# 以后装好 Docker/K8s，只需改成真实命令，函数签名不变
def get_pods(namespace="default"):
    import subprocess
    result = subprocess.run(["kubectl", "get", "pods", "-n", namespace], ...)
    return result.stdout
```

Agent 的代码**完全不用改**——它只知道"有个叫 get_pods 的工具"，不关心工具内部是模拟还是真实。

这就是"面向接口编程"：Agent 与工具解耦，让系统可测试、可演进。

## 六、面试可能被问的点

1. **工具调用（Function Call）的原理**：大模型输出结构化 JSON（工具名+参数），程序解析并执行，结果再喂回。
2. **ReAct 是什么**：Reasoning + Acting 循环，Agent 通过"思考-行动-观察"迭代解决问题。
3. **为什么要用模拟工具**：在没有真实环境时先验证机制；也方便单元测试。
4. **工具的安全问题**：不能让 LLM 随便执行危险命令，需要白名单、只读优先、二次确认（阶段④会做）。
5. **工具调用和 RAG 的区别**：RAG 是"查资料"，工具调用是"做动作"；两者可以结合（Agent 既能查知识库又能执行操作）。
