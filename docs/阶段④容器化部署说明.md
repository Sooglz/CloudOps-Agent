# 阶段④：容器化部署

> 这是 CloudOps Agent 四阶段路线的最后一步，也是最贴合「云计算」专业的部分。  
> 目标：把 Agent 打包成容器镜像，并部署到 Kubernetes 集群。



---

## 一、这一步做了什么

| 交付物      | 文件                           | 作用                                |
| -------- | ---------------------------- | --------------------------------- |
| 镜像构建定义   | `Dockerfile`                 | 把 Agent 打包成容器镜像                   |
| 构建忽略清单   | `.dockerignore`              | 排除 .venv/.env 等，减小镜像、防密钥泄露        |
| K8s 部署清单 | `deploy/cloudops-agent.yaml` | Secret + Deployment + Service     |
| 真实命令工具   | `src/tools.py`               | 模拟工具升级为真实 kubectl/docker 命令（自动降级） |

## 二、Dockerfile 的核心知识点

```dockerfile
FROM python:3.12-slim      # ① 基础镜像
WORKDIR /app               # ② 工作目录
COPY requirements.txt .    # ③ 先复制依赖清单
RUN pip install -r ...     # ④ 装依赖
COPY src/ ./src/           # ⑤ 复制源码
CMD ["python", "src/app.py"]  # ⑥ 启动命令
```

**面试重点：为什么先 `COPY requirements.txt` 再 `COPY src/`？**

Docker 构建是分层的，每一层有缓存。依赖清单（requirements.txt）通常很少变，而源码频繁变。  
把依赖安装放前面，源码放后面，这样每次改代码重新构建时，依赖层命中缓存，  
不用重新下载安装，构建速度大幅提升。这是 Docker 最佳实践。

**另一个重点：为什么 `.env` 不能 COPY 进镜像？**

`.env` 里有 API Key 密钥。一旦 COPY 进镜像，密钥就会永久存在镜像的某一层里，  
任何人拿到镜像都能 `docker history` 还原出密钥。正确做法是运行时通过  
`--env-file` 或环境变量注入（见下面）。

## 三、构建与运行

### 1. 构建镜像

```bash
cd D:\Work\CloudOps-Agent
docker build -t cloudops-agent:latest .
```

### 2. 运行容器（交互式对话）

```bash
docker run -it --rm --env-file .env cloudops-agent:latest
```

`--env-file .env`：把本地的 .env 里的环境变量注入容器（密钥不进镜像）。  
`--rm`：容器退出后自动删除，不留垃圾。

## 四、部署到 Kubernetes

### 前置：启用 Docker Desktop 内置 K8s

Docker Desktop → Settings → Kubernetes → 勾选 Enable Kubernetes → Apply & Restart。  
等右下角显示 Kubernetes 状态为绿色（running）即可。

### 1. 部署前：替换 Secret 里的 Key

打开 `deploy/cloudops-agent.yaml`，把 Secret 里的两个占位符换成你的真实 Key：

```yaml
stringData:
  DEEPSEEK_API_KEY: "sk-你的真实key"
  ZHIPU_API_KEY: "你的真实智谱key"
```

### 2. 部署

```bash
kubectl apply -f deploy/cloudops-agent.yaml
```

### 3. 查看状态

```bash
kubectl get pods -n cloudops
kubectl get svc -n cloudops
```

### 4. 进入 Agent 对话

```bash
kubectl exec -it -n cloudops <pod名> -- python src/app.py
```

## 五、K8s manifest 的三个核心对象

| 对象             | 作用              | 类比             |
| -------------- | --------------- | -------------- |
| **Secret**     | 存 API Key 等敏感配置 | 保险柜，与代码分离      |
| **Deployment** | 管理 Pod 副本，保证高可用 | 工厂生产线，坏了自动补    |
| **Service**    | 给 Pod 提供稳定访问入口  | 前台接待，屏蔽 Pod 变化 |

**面试重点：Secret 为什么不用 ConfigMap？**

ConfigMap 存普通配置（明文），Secret 存敏感数据（API Key、密码）。  
Secret 底层做了 base64 编码（注意：base64 不是加密，只是防止"一眼看到"，  
真正安全要靠 RBAC 权限控制谁有权限读 Secret）。

## 六、真实工具调用的设计（关键亮点）

阶段③ 用「模拟工具」跑通了工具调用机制，阶段④ 升级成「真实命令」：

```python
def get_pods(namespace="default"):
    if _has_cmd("kubectl"):          # 本机有 kubectl → 执行真实命令
        return _run(["kubectl", "get", "pods", "-n", namespace])
    return _mock_get_pods(namespace)  # 没有环境 → 降级为模拟数据
```

**这个设计的好处**：

1. 有真实 K8s/Docker 环境时，Agent 真正执行 `kubectl`/`docker` 命令
2. 没有环境时自动降级，保证演示不中断
3. 函数签名不变，Agent 代码零改动

**面试必讲**：这体现了「只读工具 + 白名单」的安全意识——工具层只暴露查询命令，  
危险操作（删除/重启）需要额外的安全确认，这正是生产级运维 Agent 的设计原则。

## 七、面试可能被问的点

1. **Docker 镜像分层和缓存**：为什么先 COPY 依赖再 COPY 源码。
2. **密钥如何进容器**：绝不能 COPY 进镜像，用 --env-file / Secret 注入。
3. **Secret vs ConfigMap**：敏感 vs 普通配置。
4. **Deployment vs StatefulSet**：无状态应用用 Deployment，有状态（如数据库）用 StatefulSet。
5. **为什么工具要设计成只读**：安全，防止 Agent 误操作删除生产资源。
6. **容器里跑 kubectl 怎么连集群**：需要挂载 kubeconfig，或 Agent 部署在集群内用 ServiceAccount 权限。
